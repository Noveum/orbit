## Trust-root update boundary

Future changes to `CODEOWNERS`, any workflow or repository-local action, the lockfile, any root or workspace package or Bun configuration, or the runtime readiness checker, validator, verifier, Git reader, registry wrapper, or manifest wrapper use a dedicated policy-update pull request with both named exact-head approvals. That pull request contains only trust roots and the permitted governance, pull request template, and policy test companions. It never carries the plan, this ledger, scope audit JSON, manifest JSON, registry JSON, or product files. This boundary becomes enforceable only after the trusted workflow and external ruleset bootstrap in the [governance procedure](readiness-scope-governance.md) is complete.

## Accountability and status rules

Current `Open` rows use public role aliases. These aliases identify an accountable maintainer role, not an assigned person. Before a row enters a terminal status, its owner, decision principals, Release approver, and any security authority must resolve through the committed [reference registry data](../../scripts/readiness-reference-registry.json) to human assignments with stable opaque subject identifiers and HTTPS assignment-record links. The trusted validator is separate in [`scripts/readiness-reference-registry.ts`](../../scripts/readiness-reference-registry.ts). The registered owner role must equal the ledger role. Release approval requires the exact `Release maintainer` role, and security authority requires the exact `Security maintainer` role. Independence is checked with subject identifiers, so alternate aliases for one person do not count as independent approval.

The inert registry JSON is authored as entry arrays so duplicate source keys remain reviewable. Every record and principal, including unused entries, is validated before lookup maps are built. Human aliases point to one canonical human assignment; copied subject identifiers are not an alias model. Evidence entries declare an HTTPS URL and an evidence kind matching the `record:` namespace. The adjacent TypeScript file is trusted validator code and cannot be changed in an evidence-only closure pull request.

The closure process is squash-safe. First, an implementation pull request adds the failing test, the fix, and the passing test, then is squash-merged to `main` as candidate commit C. The implementation record binds C to the canonical `https://github.com/Noveum/orbit/pull/<number>` identity. A behavioral closure uses `test:first=record:<failing-test-key>;passing=record:<final-test-key>`. Its failing-test record binds an earlier full PR-head commit F, the same pull request identity, an exact Actions attempt URL, and a SHA-256 artifact digest. F and C must differ. Because squash merging removes the PR commit chain from `main`, the checker does not claim local F-to-C ancestry. The authenticated GitHub check instead proves that the failing run used F on a `pull_request` event for the implementation pull request and that the merged pull request reports C as its squash commit.

Direct `main` CI at C supplies the final test and release-gate evidence. Both records use exact `https://github.com/Noveum/orbit/actions/runs/<run-id>/attempts/<attempt>` URLs and SHA-256 artifact digests. While a row is `Ready for closure`, the authenticated checker requires the trusted `.github/workflows/ci.yml` workflow identity and exact definition digest at C, a `push` event at C, the named test job and `Run tests` step, every required release-gate job, and the exact unexpired `readiness-test-<sha>-<attempt>` or `readiness-gate-<sha>-<attempt>` artifact. Test, gate, decision, and approved non-behavioral records agree on C and its exact commit URL. Git proves that the program baseline precedes C, C is a proper ancestor of the evidence head, and only the ledger and inert registry JSON changed after C. Observation timestamps must order failing test, implementation, passing test, gate, and decision, and cannot be later than the injected verification instant.

After direct `main` CI succeeds, an evidence pull request changes only this ledger and `scripts/readiness-reference-registry.json`, records the complete evidence, and moves the row to `Ready for closure`. The trusted-base workflow authenticates the hosted runs and merged implementation pull request before this pull request merges as evidence commit M. The Ready snapshot and terminal seal must be different pull requests. Only after M is on `main` may a second seal pull request change the same two files, move the row from `Ready for closure` to `Closed` or `Accepted P1 exception`, and add one `record:closure/<key>` entry that binds the finding ID, C, M, an observation timestamp, and the SHA-256 digest of the exact staged finding, exception, evidence, and principal snapshot.

For a seal transition, the checker reads the ledger and inert registry JSON directly from M, requires that M recorded the row as `Ready for closure`, requires the exact ledger-and-registry change shape from C through M, and compares the historical and current snapshot digests. It derives the unique merged pull request for M and verifies the prior successful `Trusted readiness policy` status on that pull request head. The status must target the exact successful Actions run and attempt. The run's top-level target repository must be `Noveum/orbit`, while its pull request entry is bound to the number, head, and base without relying on nested repository fields that may be null. The run is also bound to the event, active readiness workflow identity, trusted workflow path, trusted workflow definition digest, and pre-merge chronology.

Hosted proof is fetched only for a transition from a Ready base row to a sealed head row. Once sealed, later pull requests with unchanged terminal rows use the durable Git record without fetching finite-retention Actions artifacts, the earlier pull request, or its status again. Later product commits do not reopen the finding because the durable record binds the reviewed snapshot at M rather than requiring all later commits to remain evidence-only. Tokenless checks still validate structure, repository ancestry, scope, chronology, and the durable seal.

The trusted-base workflow writes pending and final `Trusted readiness policy` commit statuses to each captured evidence or seal pull request head. Submitted, edited, and dismissed reviews by either named required reviewer request revalidation; unrelated reviews do not start the policy job. In supported token contexts the eligible review event refreshes the status. A fork-originated review event may receive a downgraded token and require a maintainer to rerun the current trusted `pull_request_target` job instead. Immediately before success, the checker re-fetches the current pull request and reviews, confirms that the base and head are unchanged, and repeats the exact-head approval decision for a semantic scope change. Repository administrators must separately activate and verify a ruleset that requires this explicit status, a current branch, stale-approval dismissal, and required reviewer controls. Those external review controls remain authoritative if a review event cannot write a refreshed status. The workflow has no GitHub-assigned numeric ID until its definition reaches the default branch, so the introducing pull request cannot supply that external identity or prove the ruleset is active.

The other structured fields use `implementation:record:<key>`, `gate:record:<key>`, `docs:record:<key>`, `risk:record:<key>`, `approver:principal:<key>`, and `authority:principal:<key>`. A demonstrably non-behavioral change may use `test-na:record:<key>;justification=record:<key>;approver=principal:<key>` instead of a failing test. Its non-behavioral attestation, release gate, and decision must agree on the same later candidate and appear in chronological order after implementation.

`Open` rows use the explicit placeholders `pending:open` and, only when security authority is not required, `not-required`. `In progress` requires linked implementation evidence while all unfinished test, gate, documentation, decision, and approver fields remain `pending:open`. No other placeholder is valid. `Ready for closure`, `Closed`, and `Accepted P1 exception` require implementation, change, release-gate, documentation, residual-risk, decision, and independent-approver records. `Closed` and `Accepted P1 exception` additionally require exactly one durable closure record, while earlier states must not have one. A decision is `decision:record:<key>;implementation=principal:<key>;finding=principal:<key>;approver=principal:<key>`. Its three human subjects must differ, the finding subject must equal the accountable owner subject, and the approver subject must equal the independent approver subject.

Every P0 is currently `Open` and cannot use `Accepted P1 exception`. `Security authority required` is reviewed explicitly for every finding. A security-required transition needs an independent human Security-maintainer authority; a non-security transition must use `not-required`. A P1 exception is added while its finding is `Ready for closure`, then becomes accepted only in the seal pull request. It needs an expiry after the checker's current UTC verification date and records matching its finding's owner, residual risk, decision, approver, and authority. The checker decodes entity references, normalizes Unicode and formatting controls, requires rendered alphanumeric word content, and rejects known placeholder and deferral variants. These automated checks exclude demonstrated empty and deferred forms only. Human reviewers must still determine whether the public limitation accurately describes a concrete impact and constraint.
