# PR5: Issue transaction events and reliable realtime publishing

Status: design proposal only, with no feature implementation or migrations included. The failure tests and deployments described here are planned work; documentation validation is recorded in the PR description. Evidence baseline: October 15, 2026, Asia/Shanghai. The discussion summary identifies the two items that require coordination. Section A contains the complete technical design; sections B through D cover the file estimate, test matrix, and decision boundaries. Verified facts are distinguished from proposed engineering choices. The maintainer's earlier preferences do not constitute approval of this proposal.

## Discussion summary for maintainers

This is the **fifth PR in the split of the original large PR [#512](https://github.com/Noveum/orbit/pull/512)**. Its purpose is to make event delivery reliable after an Issue transaction commits. The proposed engineering plan follows the earlier deployment direction. Two areas need coordination before the relevant work proceeds: shared realtime replay semantics and the production transition.

**Proposed scope and approach.** The first release covers PR4's 12 Issue write tools, the Core transactions shared with Human writes, and their realtime side effects. Issue changes and pending events are recorded in the same transaction. Issue realtime delivery uses a dedicated, narrow table; Slack and email remain the responsibility of the existing notification Provider Outbox. Bounded in-request processing is backed by a cron job every minute. Both call the same drain interface. A standalone self-hosted Worker is deferred. Delivery is at least once up to Redis accepting the publish, allows duplicates, and preserves sync ID, Actor, and originClientId. It does not guarantee global ordering or receipt by every client.

**Behavior and responsibility.** PR5 handles delivery retries and duplicate events. Business-request idempotency remains separate work under [#407](https://github.com/Noveum/orbit/issues/407), with no implementation dependency introduced here. When a covered Issue transaction has committed and only immediate delivery fails, the tool returns its original successful business result and background delivery retries the event. Authorization, validation, and transaction errors still fail. This behavior fix will be documented and covered by regression tests as part of ordinary PR review.

**The two coordination items:**

1. **Realtime replay protocol.** The proposal adds an optional durable action identity and allows delayed actions with lower sync IDs to bypass the global `since` filter. Per-object version checks, current authorization checks, and hub protections for older browser bundles make replay safe. This changes the semantics of the shared protocol. Is this replay direction acceptable? If the existing global filter must remain, we should agree on a narrower reference-invalidation design and its guarantee instead.
2. **Production transition and rollback.** The proposal requires a preparation release containing consumer protections and the drain, followed by draining or closing old hub connections before enabling transactional event producers. Rollback must preserve compatible consumers and backlog processing. We need to confirm whether the platform supports deploying a specified preparation build, identifying and draining old hubs, who will perform these steps, how they will be verified, and the oldest acceptable rollback version. Section A.5 provides the proposed checklist.

**Delivery and review size.** Implementation is planned as one PR with approximately **2,250-3,450 handwritten changed lines**, plus approximately **16,000-18,000 generated migration metadata lines**. Commits will be organized as consumer compatibility, storage and drain, then transaction integration. Necessary tests and the complete review size will remain visible. Scope can be adjusted through normal review. The full technical proposal follows; this draft does not enable or deploy the feature.

---

**Implementation organization.** One implementation PR will contain consumer protections, Outbox infrastructure, and Issue transaction integration rather than three separate implementation PRs. The complete implementation and necessary tests remain in scope, with commits arranged for review. An explicit request during review to narrow or split the work can be accommodated. A single PR does not remove the need for staged deployment or compatibility verification with the production operator.

## A. Complete technical design

The following is the proposed engineering plan. Shared protocol changes and the production transition are the two separately coordinated items.

### 1. Actual call chain and delivery gaps

The top-level [Issue service](https://github.com/Noveum/orbit/blob/16e4fd7be763e40ed4cd8a4a4217d67259892cfd/packages/core/src/work/issue-service.ts) transaction writes the Issue, relations/subscriptions, labels/reviewers, cycle membership, and `appendActivities(tx)`. Through `notifyRecipients(tx)` and the [service-layer `notifyMany`](https://github.com/Noveum/orbit/blob/16e4fd7be763e40ed4cd8a4a4217d67259892cfd/packages/services/src/notifications/index.ts), that same transaction writes `notification_source_event`, `notification`, `notification_conversation`, counters, and `notification_delivery`. These Issue paths have no separate `audit_log` write; PR5 does not introduce an audit product. Human creation currently reserves Issue numbers outside the transaction, permitting gaps, and that behavior remains unchanged.

The returned `SyncAction[]` currently exists only in memory. REST routes call [handler.publish](https://github.com/Noveum/orbit/blob/16e4fd7be763e40ed4cd8a4a4217d67259892cfd/apps/web/src/lib/api/handler.ts#L134), which stamps the origin after commit and catches publishing errors. MCP tools call [support.publish](https://github.com/Noveum/orbit/blob/16e4fd7be763e40ed4cd8a4a4217d67259892cfd/packages/mcp-server/src/tools/support.ts), which propagates an error that is wrapped as `isError`. Both ultimately call [publishDeltas](https://github.com/Noveum/orbit/blob/16e4fd7be763e40ed4cd8a4a4217d67259892cfd/packages/core/src/realtime/publisher.ts), then Redis, the hub, the socket, and DeltaBridge/cache.

The gaps are: a process can exit after commit but before publishing; a temporary Redis outage leaves no durable retry record; an MCP write can commit but report an error because publishing failed; a silent return without `REDIS_URL` can be mistaken for success; and a process can exit after publishing but before recording completion, requiring duplicate delivery. Durable notification Provider delivery does not make notification realtime actions durable.

**Adapter observation at the fixed `main` baseline.** `notificationsByEntity` groups by `data.entityId`, but new `notification_conversation` actions have no such field, so update/bulk in-memory aggregation can omit that side effect. The proposal uses a complete notification sidecar at transaction scope, aggregated once at the top level. This is a source observation at the fixed `main` commit, not a claim of an outstanding PR4 review defect.

### 2. Initial coverage and atomic recording

**Initial coverage.** Align with PR4's 12 Issue write tools and their Core paths shared with Human writes: create, update, create_sub_issues, bulk_update, move, move_to_cycle, archive, unarchive, delete, set_relation, remove_relation, and mark_issue_duplicate. Include the Issue/relation/subscription actions they generate, move source-departure and destination/rebalance actions, child Issue updates after deletion, and the complete notification/conversation/counter action set. Activities and cycle-analysis rows remain transactional without adding new public event types.

Independent subscribe/unsubscribe, comments, attachments, GitHub/sprint/import, and other writers are deferred. The first release does not claim reliable delivery for every Issue mutation in the repository. PR1-4 identity, authorization, Owner/Assignee, Human behavior, and compatibility columns remain intact; the PR6 contract migration is not brought forward.

Before each actual top-level business transaction returns, it calls `stageIssueEvents(tx, completeActions, deliveryContext)` once. Bulk/sub operations stage only after all work completes. Relation/duplicate delegation stages only at the layer that owns the transaction; internal helpers do not stage again. Failure to write the Outbox rolls back the whole transaction; recording after commit is prohibited. Web validates and passes `originClientId` before entering Core; cron does not invent a new origin. Store the Actor, canonical Creator/Assignee/Owner, original sync ID, and timestamp already shaped by PR4. Draining neither recalculates the Actor nor reauthorizes the original write request.

**Storage.** Add a narrow `issue_realtime_outbox` table with one row per action. A transaction shares one UUIDv7 `eventId`; `eventOrdinal` is the action's position in the complete action set. The composite primary key is the stable action identity. Store organization, payloadVersion, an allowlist-validated SyncAction, minimal delivery scope, status, availableAt, attempts, claimToken, leaseExpiresAt, publishedAt, and errorCode. The wire format gains optional paired `eventId`/`eventOrdinal` fields; older messages remain valid. The compatible fields receive normal implementation review; their replay and `since` semantics are coordinated under D.1. This identity is for delivery replay, not request idempotency: executing the same MCP business request again can still write again.

Returned actions carry their durable identity. For those actions, the publishing adapter at covered entry points triggers the drain instead of direct publishing. Uncovered actions retain the existing path; an action must not use both paths. If commit succeeds and immediate draining fails, REST/MCP returns the original successful business payload/deltas without a new public status field. Isolate delivery errors only; do not swallow authorization, validation, transaction, or unrelated tool errors. Post-commit describe/decoration reads and a network disconnect can still leave the caller uncertain. This proposal does not eliminate all request ambiguity.

**MCP responsibility and behavior.** Returning success after commit when only delivery fails is an explicit behavior fix, documented prominently and covered by regression tests under ordinary review. PR5 adds no generic request key, response cache, or business-execution reclaim. Business-request idempotency remains separate work under #407. Coordination with that work is needed only if an interface changes, implementation is reused, a dependency is introduced, or an actual implementation conflict appears.

### 3. Provider boundary and bounded draining

The existing [Provider Outbox](https://github.com/Noveum/orbit/blob/16e4fd7be763e40ed4cd8a4a4217d67259892cfd/packages/services/src/notifications/provider-outbox.ts) remains solely responsible for Slack, email, and similar delivery. Reuse the records/plans from `notifyMany(tx)` and the established patterns for claimToken fencing, short transactions, deadline/clock handling, health metrics, and cron authentication. Do not duplicate fan-out, recipient deduplication, or Provider queues. A separate narrow table is appropriate because `notification_delivery` recipient/thread/namespace rules, Slack's ambiguous-delivery barrier, and Resend's 23-hour idempotency window differ from repeatable Redis state synchronization. Do not extract a generic queue framework at this stage. This boundary requires no coordinated change to the Provider system.

Interfaces and initial budgets: `stageIssueEvents(tx, actions, context)`, `drainIssueEvents({eventRefs?, organizationId?, limit, batchSize, concurrency, deadlineAt, now?})`, `issueEventHealth()`, and `pruneIssueEvents()`. A request drains only its newly committed actions, defaulting to at most 10 rows, concurrency 2, and a total budget of 250 ms. A new `/api/cron/issue-events` route in the same project runs every minute independently of the longer-running notification cron, defaulting to 100 rows, batches of 20, concurrency 4, a 20-second total budget, and route `maxDuration` of 30 seconds. Reuse `CRON_SECRET` authentication: missing configuration returns 503; invalid credentials return 401. These are tunable initial engineering values, not throughput or latency SLAs.

**First-release Worker scope.** Requests and cron call the same drain interface. The first release provides the interface and operating constraints needed by a future self-hosted Worker. A standalone persistent process, service orchestration, and Worker deployment package are deferred. This implements the earlier optional-Worker direction. A later expansion will update the file, operations, test, and handwritten-size estimates.

Claiming uses database time. A short transaction uses `FOR UPDATE SKIP LOCKED` to select due pending/retry rows or expired processing rows, then writes a random claimToken, attempts, and a 30-second lease. Network calls do not hold the claiming transaction open. Before each send and each completion/failure update, check the token, state, and unexpired lease; a stale claimant cannot overwrite a newer result. Stop claiming new batches when time is insufficient. Conditionally release held rows that were not sent; leases recover rows after a process exits. Redis uses a fast-failure publishing path, disables offline queuing, and bounds each command to approximately 100 ms subject to the remaining budget. A silent return from the existing publisher cannot count as success. Database claim/finalize operations also need short statement/lock timeouts; timing out a Promise while leaving a query running is insufficient.

Failures use exponential backoff with full jitter, initially starting at 1 second and capped at 5 minutes. Temporary Redis failures continue retrying rather than being discarded after an attempt limit. Unknown payloadVersion or malformed payloads become blocked, are retained with an alert, and require explicit requeue after repair. An expired claimant may already have sent a Redis command; fencing governs database state and cannot undo an external send.

### 4. Guarantees, consumers, and safety boundaries

**Delivery guarantee.** Deliverable actions from covered transactions receive at-least-once Redis publishing. When deletion or authorization boundaries prohibit resending historical content, an action can be suppressed with a recorded reason; suppressed is not published. A higher database sync ID alone does not prove an event has been superseded. Superseded completion requires a newer durable action for the same subject that covers equivalent state and audience and is already published. Pending/blocked rows and suppressed rows without an equivalent replacement do not qualify. Otherwise, deliver a valid older snapshot with its original sync ID and rely on consumers to prevent regression. Retries reuse the same `(eventId,eventOrdinal)` and do not rerun business logic, activity writes, or `notifyMany`. There is no global ordering across events and no external exactly-once guarantee. The guarantee is an explicitly documented engineering boundary; shared replay semantics remain coordinated under D.1.

**Protocol change requiring coordination.** [Sync IDs](https://github.com/Noveum/orbit/blob/16e4fd7be763e40ed4cd8a4a4217d67259892cfd/packages/core/src/sync/sync-id.ts) reflect sequence-allocation order. [Connection](https://github.com/Noveum/orbit/blob/16e4fd7be763e40ed4cd8a4a4217d67259892cfd/packages/realtime-server/src/connection.ts) currently drops `syncId <= subscribe.since`. This proposal allows durable actions to bypass that global filter, using action-identity deduplication and per-model/object version protection; legacy actions keep their existing protocol. Optional-field compatibility alone does not approve this semantic change. The actual [DeltaBridge](https://github.com/Noveum/orbit/blob/16e4fd7be763e40ed4cd8a4a4217d67259892cfd/apps/web/src/lib/realtime/delta-bridge.tsx) already has Issue/deletion watermarks, move-survival rules, and own-origin handling. Preserve those protections and extend replay acceptance tests. Keep strict `<` when rejecting an older full Issue version: departure and arrival with the same sync ID must not be collapsed into one action. A late source tombstone must not delete the latest row in the destination team. Exact LRU deduplication is an optimization, not a permanent correctness dependency. Own-origin events continue preserving optimistic rows while observing versions and updating derived caches.

Notifications retain hub projection to `{id,syncId}`, user scope, currently authorized conversation GETs, and monotonic `counterVersion` snapshots. They must not increment counters again on replay. A successful Redis `PUBLISH`, including a return value of zero subscribers, means only that Redis accepted the command. There is no client ACK or durable subscription-replay guarantee. [catchUp](https://github.com/Noveum/orbit/blob/16e4fd7be763e40ed4cd8a4a4217d67259892cfd/packages/core/src/realtime/backfill.ts) reconstructs current rows and cannot fully recover hard deletions or late commits with lower sync IDs. Retain `main`'s authoritative Web refresh on reconnect. Complete durable socket catch-up is deferred.

**Safety prerequisites.** Delayed replay cannot trust historical scopes alone. Before durable fan-out, both the drain and hub query current tenant/team/existence/version, not just at claim time. The hub also refreshes member/role/team reach in batches, with an authorization fence to recheck or remove stale pending actions before flush. It must not depend on the five-minute boundary cache or a revocation delta that could have been lost. Deleted or moved resources must not expose historical content; retain the existing minimal delete/departure cleanup signals. Issue bodies follow Issue versions; relations/subscriptions follow their own state and tombstones. Notifications retain reference-only projection; conversations use their own syncId/counterVersion. A newer parent Issue must not cause the entire notification sidecar to be discarded. Payloads that require redaction but lack a safe replacement remain blocked with an alert rather than being falsely marked complete. Query failures fail closed. Concurrent changes after the authorization check follow the existing check linearization point; already-sent bytes cannot be recalled.

**Engineering responsibility for older browser bundles.** Before implementation, classify each action type against the final baseline: safe to send unchanged, requires filtering/projection, or blocked because no safe representation exists. Cover those rules with tests. In particular, do not assume subscription consumers have an independent version watermark. If an old insert/delete conflicts with the current subscription state, the hub must stop it reaching an older browser. Check relations and notification side effects against their own state as well. Where client convergence requires a representation the existing protocol cannot express safely, include reference invalidation or current-state projection and its version source in the first coordination item under D.1. Do not add a public message type implicitly, or treat dropping an action as successful delivery. Both older and newer Web bundles must pass duplicate, out-of-order, and same-ID move tests. These details and tests are engineering obligations, not a third approval item. They are not implemented yet.

Hard-delete/departure payloads retain only necessary references such as `{id,teamId,identifier,syncId,departure?}` and do not cascade away through an Issue foreign key. Organization deletion may clear them under existing tenant-deletion semantics. Actor/responsibility history is preserved; later Grant revocation does not erase a committed fact. Delivery is authorized against current readers. A strict allowlist excludes tokens, internal Grant IDs, original request bodies, and unrelated content; logs do not emit payloads. Notification permission/preference changes remain the responsibility of existing Provider preflight checks.

### 5. Operations, mixed versions, and rollback

Initial retention is seven days after a row reaches published/suppressed, with bounded daily pruning. Delete only terminal rows with a cleared claim and no active lease. Do not age-delete pending/retry/processing/blocked rows. Routine payload retention follows this window; organization deletion uses tenant-deletion rules. Minimum metrics include counts by state, oldest unfinished age, expired leases, attempts, publishing failures, suppression reasons, and blocked count. Alert when backlog age exceeds five minutes or blocked rows appear. Troubleshooting requires only event references, organization/model/modelId, state, attempts, error code, times, and a request correlation ID, without payload content or credentials.

**Production transition requiring coordination.** One PR5 contains two buildable release artifacts: a preparation artifact with consumer protections, the additive table, and drain/cron but no business producer integration; and a final artifact that enables transactional event recording. Implementation will pin their commits and verification records without requiring another PR. Apply the additive migration and deploy the preparation artifact first. Confirm that all live hubs, including long-lived connections from an earlier deployment, have the protections before deploying the final artifact. The preparation stage must be verified before a merge triggers final deployment. Parsing compatibility for an older browser does not establish replay safety; hub filters and compatibility tests must protect it without relying on asking users to refresh. No new feature flag is proposed: producer integration switches with the final artifact. Agent write gates and `NOTIFICATION_PROVIDERS_PAUSED` do not control the drain. During mixed-writer operation, old-writer requests retain only their existing direct-publish guarantee; full coverage begins when all writers are upgraded. Platform feasibility and operator responsibility are the second coordination item under D.1.

**Transition checklist to agree with the production operator:**

1. Pin the source SHAs, build identifiers, migration, and verification records for the preparation and final artifacts. Confirm that the platform can deploy the specified preparation artifact independently before merging triggers final deployment. Passing PR CI is not a production deployment record.
2. After deploying the preparation artifact, the operator inventories deployments that can still handle requests or long-lived connections and checks hub build versions and connection records. Route new connections to the preparation version, stop admission to older deployments, and drain or close old WebSockets using supported platform mechanisms. Switching HTTP traffic alone does not prove old hubs have exited. The release runbook must identify inspection entry points, version records, and disconnection mechanisms.
3. Acceptance includes browsers opened before the upgrade. Verify that the new hub supplies the per-action protections in A.4 without assuming the browser fetches a new bundle automatically. Record that old deployments/connections have exited, current authorization checks work, and the preparation artifact can process the final artifact's payloadVersion.
4. Deploy the final artifact and enable producer recording only after these records exist. If old hubs cannot be enumerated or drained, or older-browser compatibility fails, stay at the preparation stage without enabling the new producer. Retain any existing backlog and process it with the safe preparation version. If the platform cannot provide verifiable transition conditions, coordinate protocol-version recognition, activation conditions, or a narrower reference-invalidation design before proceeding. Do not implicitly add a new gate or weaken safety guarantees.

Producer rollback uses the compatible preparation artifact from the same PR, preserving the consumer safety baseline and compensating cron so backlog processing continues. A whole-site rollback in the single project must retain these capabilities. If only an unsafe older hub can be restored, stop publishing first, retain the backlog, and restore a compatible drain as part of incident recovery rather than deleting or indefinitely abandoning events. Unknown newer payload versions remain blocked. Do not drop the additive table or compatibility columns. The minimum application rollback version after Agent rows exist still follows PR4; PR5 does not alter PR3's stage 3a/3b deployment sequence.
